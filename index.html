DevSecOps Enterprise Academy

A beginner-friendly field guide to how a very large company builds, ships and protects software. Prepared for Piyush. Reader level: first-year B.Tech student. Numbers and company names are illustrative, to show the shape of real life.

Part 1. The Big Picture: A Company Is a City

Forget software for a moment. Picture a huge city such as Mumbai.

  • Layer 1 (websites and apps) = the shopfronts, signboards and showrooms. What visitors see and touch.
  • Layer 2 (backend services) = the kitchens, workshops and delivery desks behind the shop. Where the real work happens.
  • Layer 3 (business systems and databases) = the municipal record office and the giant warehouses. Where the official records live: customers, orders, salaries, stock.
  • Layer 4 (infrastructure) = land, roads, electricity, water and buildings. Where everything physically sits and runs.

Security is the police, locks, CCTV and building inspectors. DevSecOps simply means: the building inspector walks around while the building is being constructed, not after it is finished and full of people. Cheaper, faster, safer.

One sentence to remember: Dev (build it) + Sec (protect it) + Ops (run it) = one team, one automated conveyor belt, checks at every step.

Part 2. The Four Layers, Deeper

Layer 1: Websites and user interfaces

Analogy: the shop window and the billing counter.

What lives here: the public brand website, the mobile app, the customer portal, the internal HR portal, the admin dashboard.

Built with: HTML/CSS/JavaScript, React, Angular, Android (Kotlin), iOS (Swift). Developers write this in VS Code, Android Studio or Xcode.

Who uses it: customers (external) and employees (internal).

What goes wrong: cross-site scripting (XSS), insecure login pages, secrets accidentally left in JavaScript, tampered third-party scripts.

Layer 2: Backend applications and microservices

Analogy: a food court kitchen. Instead of one giant kitchen doing everything, there are small specialised stalls: one makes only dosa, one only juice, one only billing. Each stall is a microservice. They pass orders to each other through the counter (an API).

Examples: Product API (what can be sold), Order Service (placing the order), Payment Service, Authentication Service (who are you?).

Built with: Java, Python, Go, Node.js, .NET. Developers use IntelliJ, PyCharm, Visual Studio, VS Code.

What goes wrong: broken access control (a customer reading another customer's order), SQL injection, vulnerable libraries, services trusting each other too much.

Layer 3: Enterprise business systems and databases

Analogy: the government record office plus the central warehouse. Slow to change, extremely important, heavily guarded.

Examples: SAP (finance, stock, procurement), Oracle/PostgreSQL/MySQL databases, CRM (customer records, e.g. Salesforce), HR systems (salaries, leave), data warehouses.

Why they matter: if a shopfront is defaced, it is embarrassing. If this layer is stolen or corrupted, the company can stop operating. This is where the crown jewels sit.

What goes wrong: over-privileged accounts, unpatched databases, publicly exposed database ports, no encryption, no backups.

Layer 4: Infrastructure

Analogy: land, buildings, electricity and roads. You can own land (your own data centre) or rent it (cloud).

Examples: AWS (EC2 servers, ECS containers, S3 storage), GCP (GKE Kubernetes, Cloud Storage, Vertex AI), Alibaba Cloud (ACK, OSS), networking (VPCs, firewalls, load balancers), Kubernetes.

What goes wrong: public storage buckets, open firewall rules, over-powerful cloud roles, unpatched servers, leaked cloud keys.

One click, all four layers

A customer taps Buy Now:

  1. Layer 1: the app sends the request.
  2. Layer 2: the Authentication Service checks the login, the Order Service creates an order, the Payment Service charges the card.
  3. Layer 3: the order is written into the database; SAP is told to reduce stock and raise an invoice.
  4. Layer 4: every step above ran on servers or containers in a cloud, connected by networks.

A weakness in any layer can break the whole chain. That is why security cannot be one team at the end.

Part 3. How a Very Large Organisation Really Looks

A small project has one repo and one server. A very large organisation looks more like this (illustrative):

Thing Typical size
Engineers 5,000 to 30,000
GitHub organisations 5 to 40
Repositories 3,000 to 50,000
Microservices hundreds to thousands
Cloud accounts/projects hundreds (one per team per environment)
Clouds often 2 or 3 (AWS + GCP + Alibaba Cloud)
Kubernetes clusters dozens

Nobody can hold this in their head. So large companies depend on automation, standard rules and clear ownership. Security people cannot read every line of code; they build guardrails that check everything automatically.

3.1 GitHub structure: the company library

Think of GitHub as a giant library. An Enterprise account is the whole library building. An Organisation is a floor. A repository (repo) is one bookshelf. Teams decide who may borrow or edit what.

Example for a fictional company, Acme Retail:

Organisation What lives here Strictness
acme-retail-apps Production code for shop, orders, payments Very high
acme-platform Shared infrastructure: Terraform, Helm charts, pipeline templates Very high
acme-data-ml Data pipelines, ML models, Vertex AI notebooks High
acme-erp-integrations Connectors to SAP, CRM, HR High
acme-security Security tools, custom scanner rules, detection code Very high
acme-sandbox Experiments, hackathons, learning, proofs of concept Low, but isolated

Why so many organisations instead of one?

  • Access separation: a marketing web developer should not even see payment code.
  • Compliance: auditors can inspect one organisation without touching the others.
  • Acquisitions: when a company buys another, the new company arrives with its own organisation.
  • Blast radius: if one organisation is compromised, the others are not automatically exposed.

Rules the security team enforces on important repos:

  • Direct pushes to the main branch are blocked; every change needs a pull request (PR).
  • At least one or two reviewers must approve; CODEOWNERS forces the right experts to review the right folders.
  • Required checks (secret scan, code scan, dependency scan) must pass before merge.
  • Single sign-on (SSO) and mandatory MFA.
  • Secret scanning with push protection turned on.

3.2 The Sandbox organisation

Analogy: a school science lab. You may mix chemicals, make a mess, explode a balloon. But the lab has thick walls, no connection to the main building's gas line, and nothing leaves without a teacher checking it.

Sandbox rules in a well-run company:

  • No production secrets, no production data, ever.
  • Cannot reach production networks or production cloud accounts.
  • Repos may auto-expire or be archived after some months.
  • Code can only reach production by being re-submitted into a real organisation through the normal PR and review path. No copy-paste shortcuts.
  • Even here, basic secret scanning stays on, because people paste real keys into experiments more often than you would believe.

3.3 Environments: Dev, QA, Staging, Prod

Analogy: a wedding catering company. Dev is the chef experimenting in the home kitchen. QA is the tasting session with the family. Staging is the full dress rehearsal in the real hall. Prod is the actual wedding with guests.

Environment Purpose Data Who can access How strict
Dev Developers try and break things Fake or tiny sample data All developers Low
QA / Test Testers verify features, run automated tests Fake, realistic-looking data QA team, some developers Medium
Staging / Pre-prod Final rehearsal, copy of prod setup Masked or synthetic data Small release team High
Prod Real customers, real money Real data Very few humans; mostly automation Very high

Golden rules:

  1. Code moves only forward: Dev, then QA, then Staging, then Prod. Never edit production directly.
  2. The same container image that passed QA is the one promoted to Prod. You do not rebuild; you promote. (Same sealed lunchbox, not a freshly cooked one.)
  3. Each environment has its own cloud account or project, own Kubernetes cluster or namespace, own secrets. A leaked Dev key must be useless against Prod.
  4. Real customer data never goes below Prod, unless masked.

3.4 Why multiple clouds (AWS, GCP, AliCloud)?

Companies rarely choose just one:

  • History: one team started on AWS, another on GCP, an acquired company used something else.
  • Strengths: some teams choose GCP for data/AI (BigQuery, Vertex AI), others AWS for breadth of services.
  • Geography and law: to serve customers in mainland China, a company typically needs to run there, and Alibaba Cloud is a major local provider. Data-residency laws also shape where data may sit.
  • Resilience and negotiating power: not depending on a single vendor.

The security consequence: three clouds means three sets of settings, roles and logs to protect. That is exactly why a tool that looks across all of them (see WIZ below) is valuable.

The simplest way to place a tool: ask Where does it run, and what job does it do?

4.1 The developer's desk: IDEs

Visual Studio A big professional workshop .NET, C#, C++, Windows applications

They run on the developer's laptop (or a cloud workspace). Security helpers here are plug-ins such as SonarLint, Snyk or Semgrep extensions, and secret-detection hooks. They are advice, not enforcement: a developer can switch the plug-in off.

Key insight: enforcement never lives on the laptop. It lives at GitHub and in the pipeline, like airport security. You cannot rely on passengers promising they have no knives.

4.3 Where WIZ fits

WIZ is a cloud security platform. Imagine a drone that flies over your entire cloud city, across AWS, GCP and Alibaba Cloud, without you installing anything inside each building (this is called agentless scanning). It reads the configuration and looks inside workloads to build a map of everything: servers, containers, databases, identities, network paths.

Its special skill is connecting the dots. One small problem alone is low risk. But a toxic combination is dangerous: for example, a server that is publicly reachable + has a known critical vulnerability + holds an over-powerful cloud role that can reach a database with customer data. WIZ highlights that chain so the team fixes what is truly urgent first, rather than drowning in 10,000 low-priority alerts.

Placed in our map, WIZ works at two ends:

  • Left side (before deploy): WIZ Code scans source repos, Terraform and container images in the pipeline, and can block risky changes.
  • Right side (after deploy): WIZ looks at what is actually running in GKE, EC2 or ACK and tells you what is exposed right now.

When both ends are linked, you can trace a risk in production back to the exact repo and team that created it, and fix it at the source. That is the heart of DevSecOps.

Part 5. The Life of One Code Change

Meet Ravi, a developer at Acme Retail. He must add a discount field to the Order Service.

  1. Ticket. A Jira ticket arrives. If the change touches payments or login, a short threat-modelling chat happens first: what could an attacker do with this?
  2. Laptop. Ravi opens PyCharm (or VS Code), creates a branch from the acme-retail-apps/order-service repo, and writes code. SonarLint underlines a risky line; he fixes it.
  3. Pre-commit. A local hook blocks the commit because he pasted a test API key. Saved by a metal detector.
  4. Pull request. He pushes the branch and opens a PR. The main branch is protected, so merging is not yet possible.
  5. Automatic checks. GitHub Actions starts: secret scan, CodeQL, dependency scan, unit tests. One dependency has a critical vulnerability. The PR is blocked with a clear message.
  6. Fix and review. Ravi upgrades the library. A teammate and a CODEOWNER review and approve.
  7. Merge, then build. The pipeline builds a container image, scans it, generates an SBOM (a parts list), and digitally signs the image so nobody can swap it later.
  8. Dev deploy. The image is pushed to the registry and automatically deployed to the Dev cluster.
  9. QA deploy. Automated integration tests and a DAST scan run against QA. Testers also check by hand.
  10. Approval gate. For Prod, a named approver (release manager) must click approve. Policy checks confirm the image is signed and has no critical findings.
  11. Prod deploy. The cluster admission controller verifies the signature again. The image rolls out gradually (a few pods first, then more).
  12. Watch. WIZ and monitoring continue to watch the running service. If a new vulnerability is announced next month, WIZ flags it and the owning team is alerted automatically.

Notice Ravi never logged in to production. Humans write and approve; machines deploy.

Part 6. The DevSecOps Pipeline and Its Security Gates

Shift left means moving security checks earlier (to the left on the timeline). Fixing a bug on your laptop costs minutes; fixing it in production costs days, money and reputation.

Stage Security activity Gate decision
Plan Threat modelling, security requirements Risky features need review
Code IDE plug-ins, pre-commit secret hooks Advice only
Pull request Secret scan, SAST, SCA, IaC scan, peer review Block on secrets and criticals
Build Hardened base image, container scan, SBOM, image signing Block on critical vulnerabilities
Test (QA) DAST, integration tests, API security tests Block on high-severity findings
Release Policy check, approval, change record Needs named approver
Deploy Admission control: only signed, approved images Block unsigned images
Operate WIZ runtime view, logs, alerting, patching, incident response Fix by severity and exposure

A sensible gate policy for beginners:

  • Critical: block the merge or deploy.
  • High: block, or allow only with a written exception and an expiry date.
  • Medium/Low: warn and create a ticket with a deadline.

Strict gates with no exceptions cause developers to find ways around them. Good DevSecOps is strict where it matters, easy everywhere else.

Part 7. Hands-On Lab: Build Your Own Secure Automated Deployment Workflow

You learn this by building a small version of the real thing. Use a free GitHub account, a tiny app (a Python Flask hello-world or similar), and a free local cluster such as kind or minikube. You can later point it at GKE.

Lab architecture

  • Organisation: my-academy-sandbox (your safe lab)
  • Repo: hello-orders (the app, a Dockerfile, a Kubernetes manifest)
  • Pipeline: GitHub Actions
  • Registry: GitHub Container Registry, or Artifact Registry if you use GCP
  • Environments: dev, qa, prod (GitHub Environments, with required reviewers on prod)
  • Cluster: three namespaces (dev, qa, prod) on a local cluster

Step-by-step plan

Week 1: Foundation. Create the organisation and repo. Turn on branch protection: PRs required, one reviewer, status checks required. Turn on secret scanning with push protection and Dependabot alerts. Add a CODEOWNERS file.

Week 2: Scan on every PR. Add secret scan, CodeQL (SAST) and dependency review. Deliberately commit a fake key and a vulnerable library to watch the gates block you. Breaking it on purpose is the best teacher.

Week 3: Build safely. Write a minimal Dockerfile (small base image, non-root user). Build the image in the pipeline, scan it, produce an SBOM, sign it with cosign, push it to the registry.

Week 4: Deploy with guardrails. Deploy to dev automatically, qa after tests, prod only after manual approval. Add a policy (Kyverno or Gatekeeper) that rejects unsigned images and containers running as root.

Week 5: Watch and respond. Connect your cloud account (if you use one) to WIZ at work or explore a trial. Practise tracing a finding back to the repo. Write a one-page incident runbook.

Starter workflow (simplified)

This is a teaching skeleton. In real companies, you pin every action to a full commit SHA (not just a version tag), because pipelines themselves are a target for attackers.

name: secure-pipeline
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  secrets-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: gitleaks/gitleaks-action@v2

  sast:
    runs-on: ubuntu-latest
    permissions:
      security-events: write
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: github/codeql-action/init@v3
        with:
          languages: python
      - uses: github/codeql-action/analyze@v3

  dependency-review:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/dependency-review-action@v4
        with:
          fail-on-severity: high

  build-scan-push:
    needs: [secrets-scan, sast]
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build image
        run: docker build -t hello-orders:${{ github.sha }} .
      - name: Scan image (fail on critical)
        uses: aquasecurity/trivy-action@0.28.0
        with:
          image-ref: hello-orders:${{ github.sha }}
          severity: CRITICAL
          exit-code: '1'
      # next: generate SBOM, sign with cosign, push to registry

  deploy-prod:
    needs: build-scan-push
    runs-on: ubuntu-latest
    environment: prod   # required reviewers set in repo settings
    steps:
      - run: echo 'deploy the SAME signed image here'

What each part teaches you:

  • permissions: contents: read = least privilege for the pipeline itself.
  • needs: = ordering, the conveyor belt must pass checkpoint A before B.
  • exit-code: '1' = the gate that actually blocks.
  • environment: prod = the human approval checkpoint.

Cloud-authentication tip: never store long-lived cloud keys as GitHub secrets if you can avoid it. Use short-lived identity federation (OIDC) so the pipeline gets a temporary pass instead of a permanent key.

Part 8. Real Scenarios: How It Feels on the Job

Scenario 1: A key is leaked in a public repo

A developer commits a cloud access key to a repo that turns out to be public.

  1. Revoke the key first. Always before cleaning the repo, because bots find keys in minutes.
  2. Check cloud logs to see whether it was used.
  3. Remove it from history, add push protection so it cannot repeat.
  4. Write a short note on how it happened. No blame, just fix the process.

Scenario 2: A new critical vulnerability is announced on a Friday

The library (think Log4Shell-style) is used in hundreds of repos.

  1. Ask the question: where do we use it? SBOMs and tools like WIZ answer this in minutes instead of weeks.
  2. Prioritise: which affected services are internet-facing and in Prod? Those first.
  3. Open tickets automatically to the owning teams with a deadline.
  4. Meanwhile, add a temporary protection (e.g. a firewall rule) while patches roll out.

Scenario 3: A public storage bucket in Prod

WIZ raises an alert: a bucket with customer files is public.

  1. Confirm and close the exposure immediately.
  2. Find the Terraform in the repo that created it; fix the code, not only the bucket, otherwise the next deploy reopens it.
  3. Add an IaC policy so this mistake fails the pull request in future.

Scenario 4: Sandbox code wants to go live

A hackathon prototype impresses leadership.

  • Rule: it cannot simply be copied. It is re-built in the proper organisation, through PRs, scans, review, and proper environments.
  • Check the prototype for hard-coded secrets and test credentials first.

Scenario 5: Dev environment hacked

Because Dev has separate accounts, separate secrets and fake data, the damage is contained. This is the payoff of environment separation. The lesson is also to treat Dev as less trusted, but not as unprotected.

Part 10. Common Beginner Mistakes

  • Treating security as a final exam instead of a daily habit.
  • Trusting IDE plug-ins as protection; enforcement belongs in GitHub and the pipeline.
  • Using one cloud account for everything; Dev and Prod must be separated.
  • Rebuilding images per environment instead of promoting the same signed one.
  • Giving the pipeline or a service admin rights it does not need.
  • Turning on every scanner at maximum strictness on day one; developers then ignore all of them. Start with criticals, then tighten.
  • Fixing the running resource but not the code or Terraform that created it.

Glossary

  • API: a counter where one program places an order with another.
  • CI/CD: automatic build/test (CI) and automatic delivery (CD).
  • Container: a sealed lunchbox holding an app and everything it needs to run.
  • Kubernetes (K8s): the system that decides which servers run which containers and restarts them when they fail.
  • Namespace: a separate room inside a cluster.
  • IaC (Infrastructure as Code): building infrastructure from written blueprints instead of clicking around.
  • SAST / SCA / DAST: scanning your source / your imported libraries / your running app.
  • SBOM: a parts list for software.
  • Least privilege: give only the access actually needed.
  • Blast radius: how much damage one failure or breach can cause.
  • Shift left: do security checks earlier in the timeline.
  • Toxic combination: several smaller risks that together form a real attack path.
  • OIDC federation: a temporary pass for the pipeline instead of a permanent key.

Part 12. Inside a Real Production System

12.1 The journey of one request, hop by hop

Analogy: catching a flight. You travel by road, pass the gate security, check in, wait at the gate, board, and your bags travel separately. Each stop has its own checks. A customer request travels through similar stops:

Hop Component Airport analogy Security job
1 DNS Looking up the airport address Prevent hijacking of the domain name
2 CDN and WAF (Cloudflare, Cloud Armor, CloudFront, Akamai) Outer road checkpoint Absorbs attack traffic, blocks common web attacks, rate-limits bots
3 Load balancer Traffic police sending cars to open lanes Terminates HTTPS, hides internal servers
4 API gateway (Apigee, Kong, AWS API Gateway) Check-in desk Checks identity token, applies rate limits, validates requests
5 Ingress inside Kubernetes Terminal entrance Routes to the right microservice
6 Microservices Airline departments Business logic, authorisation per action
7 Service mesh (Istio, Linkerd) Secure internal corridors Encrypts service-to-service traffic (mTLS), says who may call whom
8 Message queue (Kafka, Pub/Sub, SQS) Baggage conveyor Carries work between services without waiting
9 Cache (Redis) Sticky note at the desk Speeds up reads; must not hold secrets unprotected
10 Database (PostgreSQL, Cloud SQL, DynamoDB) Records vault Encrypted, private network only, strict accounts
11 Integration layer to SAP and CRM Diplomatic liaison office Controls what leaves and enters the legacy world

One weak hop can undo all the others. A perfect WAF does not help if the Order Service lets any logged-in user ask for any order number (a broken access control flaw, also called IDOR). That is a code problem, which is why AppSec and scanners still matter.

12.2 Networks: gatehouse, offices and vault

A VPC (Virtual Private Cloud) is your own fenced compound inside a cloud. Inside it you create subnets, which are separate zones:

  • Public zone (DMZ): only things that must face the internet, such as load balancers. Think reception hall.
  • Private application zone: your Kubernetes nodes and services. No direct internet access in. Think back offices.
  • Data zone: databases and caches. Reachable only from the application zone. Think the vault.

Firewall rules decide who may talk to whom. A good rule is specific (service A to database B on one port). A bad rule is 0.0.0.0/0 (the whole internet) on a database port. WIZ regularly finds exactly this.

Egress (traffic going out) matters too. If a hacked container can call any website, it can download attack tools and send your data out. Mature companies force outbound traffic through a NAT gateway or proxy with an allow-list.

Connecting to the old world: SAP often sits in the company's own data centre. A VPN or a dedicated line (Cloud Interconnect, AWS Direct Connect) joins the cloud network to it. Admins reach private machines through a bastion or an identity-aware proxy (Google IAP) rather than exposing SSH to the internet.

12.3 Phone call versus letter: synchronous and asynchronous

  • Synchronous (phone call): the Order Service calls the Payment Service and waits for an answer. Simple, but if Payment is down, Order is stuck.
  • Asynchronous (letter in a postbox): the Order Service drops a message into a queue and moves on. Payment picks it up when ready. More resilient, but harder to trace.

Security view: queues need their own access control (who may publish or read), messages may carry personal data so they need encryption, and a poisoned message can crash a consumer. These are classic places where testers find surprises.

12.4 The legacy reality: SAP, CRM, HR systems

Modern teams ship daily. SAP landscapes change slowly and carefully. Real facts about this world:

  • SAP has its own DEV, QAS and PRD systems and its own promotion mechanism called transports. So even the old world has dev, test, prod, only with heavier approval.
  • SAP publishes Security Patch Day monthly (second Tuesday), and security teams track those notes.
  • Integration usually runs through middleware (for example MuleSoft or SAP's own integration suite) using OData APIs, IDocs, RFC calls or nightly batch files.
  • The classic dangers: technical accounts with huge authorisations, segregation-of-duties violations (the same person can create a vendor and approve payment to it), and old interfaces nobody owns.

Because modernisation is slow, a DevSecOps engineer must respect both speeds: automated pipelines for microservices, and change tickets with approvals for SAP.

12.5 Data: where it lives and how it is classified

Companies label data by sensitivity so that protection matches value:

Class Example Typical protection
Public Product catalogue Integrity checks
Internal Meeting notes, internal docs Login required
Confidential Customer orders, contracts Encryption, restricted roles, audit logs
Restricted Card data, health data, national ID numbers, salaries Strong encryption, tokenisation, tiny access list, special compliance rules

Every database should be encrypted at rest (on disk) and in transit (on the wire), with keys in a key-management service (Cloud KMS, AWS KMS), backed up, and with access logged. Laws such as India's DPDP Act, the EU's GDPR and card-industry PCI DSS turn these good habits into obligations.

12.6 Identity: people, machines and pipelines

In a large company there are far more machine identities than human ones:

  • Employees sign in through a single sign-on provider (Entra ID, Okta, Google Workspace) with MFA.
  • Customers use a customer-identity system (CIAM) with social login, OTPs and so on.
  • Workloads (a pod calling a database) use service accounts or workload identities.
  • Pipelines use short-lived tokens issued through OIDC.

The golden habit: no long-lived passwords or keys anywhere if you can avoid it. Prefer identities that mint temporary credentials. Most real breaches in cloud start with a leaked key or an over-powerful role.

Part 13. How Cloud Accounts Are Organised in Real Life

13.1 Why structure matters

If all your servers live in one big cloud account, one stolen key can reach everything. So large companies slice the cloud into many small boxes, put rules on the outside of the boxes, and let teams work freely inside their own box. This is the cloud version of blast radius control.

13.2 GCP: Organization, Folders, Projects

acme.com (Organization)
 ├─ Folder: shared-services     (logging, networking, security tooling)
 ├─ Folder: prod
 │    ├─ Project: orders-prod
 │    └─ Project: payments-prod
 ├─ Folder: nonprod
 │    ├─ Project: orders-dev
 │    ├─ Project: orders-qa
 │    └─ Project: payments-qa
 └─ Folder: sandbox            (low trust, no prod network access)
  • Organization policies apply to whole folders: for example, block public IPs on VMs, block service-account key creation, restrict which regions may be used.
  • IAM roles are granted at the lowest sensible level (a project, not the whole organisation).
  • GKE clusters live inside projects. Workload Identity lets a pod act as a Google service account without any key file.
  • Shared VPC lets a central network team own the network while app teams own their workloads.

13.3 AWS: Organizations, OUs, Accounts

In AWS the strong boundary is the account. A typical pattern is one account per application per environment, grouped into Organizational Units:

  • Service Control Policies (SCPs) sit on the OU and set the maximum permissions allowed. Even an account administrator cannot go beyond them (for example: never disable CloudTrail logging, never leave allowed regions).
  • Control Tower or a custom landing zone creates new accounts with logging, networking and security already wired up.
  • Humans and pipelines assume IAM roles to get temporary access into an account instead of owning permanent users.

13.4 Alibaba Cloud: Resource Directory, Folders, Member Accounts

  • Resource Directory is the organisation tree, with resource folders and member accounts, similar in spirit to AWS Organizations.
  • RAM (Resource Access Management) is the identity and permission service. ACK is managed Kubernetes. OSS is object storage. ACR is the container registry.
  • China-specific realities: mainland China regions run as a distinct ecosystem with their own accounts and compliance steps. Websites served from mainland China need a government registration known as ICP filing, and rules about moving data across borders are strict. Security teams therefore often keep China workloads and their data flows separate and documented.

13.6 Preventive versus detective controls

This idea explains why you need both guardrails and WIZ:

  • Preventive control = a locked door. Organisation policies, SCPs, admission controllers, pipeline gates. It stops the bad action.
  • Detective control = a CCTV camera and an inspector. WIZ, audit logs, SIEM. It notices what slipped through, or what was already there before the lock existed.

No company has only locks, because rules are never perfect and old resources exist. No company has only cameras, because finding a problem after the fact is expensive. Good security is layers of both.

13.7 IAM in practice: how over-permission creates a breach path

A realistic chain that WIZ-style tools highlight:

  1. A forgotten test VM is reachable from the internet.
  2. It runs an old web framework with a known remote-code-execution bug.
  3. The VM has an attached service account with the broad Editor role (or an AWS role with wildcard permissions).
  4. That role can read the storage bucket holding customer exports.

Each item looks small in isolation. Together they are a ready-made attack path. The fix is to break any link: remove the public exposure, patch the framework, or, best of all, give the VM only the minimum role. Prioritising by path instead of by raw count of findings is the biggest practical skill in cloud security.

Good IAM habits to memorise:

  • Grant roles to groups or workload identities, not to individuals.
  • Prefer predefined narrow roles over owner or editor.
  • Use just-in-time access for production: elevated rights for a few hours, with approval and logging.
  • Keep break-glass accounts for emergencies, heavily monitored, never used for daily work.
  • Review who has access regularly; remove access when people change teams or leave.

Part 14. GitHub at Enterprise Scale

14.1 People coming and going: SSO and SCIM

With 10,000 developers, nobody adds users by hand.

  • SSO (SAML or OIDC) means developers log in to GitHub with their company identity and MFA.
  • SCIM automatically creates and removes accounts and team memberships based on the identity provider.
  • Team mapping: HR or the directory says someone joined the Payments team, so they are automatically added to the right GitHub team. When they leave the company, access disappears within hours without a ticket.

This is a security control disguised as admin convenience: offboarding is automatic, so no stale access.

14.2 Repository lifecycle

  • Golden templates: new repos are created from a template that already contains CODEOWNERS, a SECURITY.md, the standard pipeline call, a .gitignore, and a pull request template. Security is born inside the repo.
  • Naming and ownership: a repo name pattern such as team-service-purpose, plus custom properties or a catalogue entry that records the owning team, criticality and data class. Without ownership, a finding has nobody to fix it.
  • Visibility: private (selected teams), internal (everyone in the company) and public (the world). Public repos need approval from an open-source review board because mistakes become permanent.
  • Retirement: unused repos are archived. Abandoned repos with live credentials or old dependencies are a common hidden risk.

14.3 Rules enforced centrally: rulesets

Organisation-level rulesets can apply to many repos at once: protect the main branch, require pull requests, require status checks, block force pushes, require signed commits for sensitive repos. Individual repo admins cannot loosen them.

14.4 Reusable workflows: one pipeline, thousands of repos

The platform team keeps a central repo (for example acme-platform/pipeline-templates) holding the approved pipeline. A service repo needs only a few lines:

name: ci
on:
  pull_request:
  push:
    branches: [main]

jobs:
  standard-pipeline:
    uses: acme-platform/pipeline-templates/.github/workflows/secure-build.yml@v3
    with:
      language: java
      service-name: order-service
    secrets: inherit

When the security team improves the template (adds a new scanner), every repo gets it by changing one version number. This is how a small AppSec team protects thousands of repos. Required workflows and rulesets can even force the central pipeline to run whether the team wants it or not.

14.5 Runners: where pipelines physically run

  • GitHub-hosted runners: fresh virtual machines from GitHub, thrown away after each job. Easy and safe, but they sit outside your private network.
  • Self-hosted runners: machines you manage, often inside your private network so they can reach your clusters and internal systems.

Security rules for self-hosted runners: make them ephemeral (one job, then destroyed), never let untrusted code from forks or public repos run on them, and give them minimal network and cloud permissions. A long-lived runner that runs anyone's code is a treasure chest for attackers.

14.6 GitHub Advanced Security (GHAS) in daily life

Feature What it does Typical enterprise setting
Code scanning (CodeQL) SAST on pull requests and on the main branch On for all important repos; criticals block merges
Secret scanning Finds known key and token formats On everywhere; push protection blocks the commit
Dependabot alerts and updates Warns about vulnerable libraries and opens fix PRs On everywhere; auto-update PRs for patches
Dependency review Shows risk of libraries a PR is adding Required check on PRs

Triage reality: alerts have an owner (the repo's team), a severity, and a dismissal reason (false positive, used only in tests, won't fix). Security reviews dismissals for critical repos. The aim is not zero alerts; the aim is no unexamined critical alerts older than the agreed deadline.

14.7 Tokens, apps and third-party access

  • Personal access tokens are risky because they live long and act as a person. Prefer fine-grained tokens with short expiry, and better still GitHub Apps with narrow permissions.
  • Third-party integrations (every app in the marketplace you install) can read your code. An approval process checks each one.
  • The audit log is streamed into the SIEM so that suspicious actions (mass cloning, new deploy keys, org setting changes) raise alerts.

14.8 Scale problems you will meet

  • Alert flood: 20,000 findings across 4,000 repos. Fix by prioritising (internet-facing, production, critical, exploitable first) and by auto-assigning to owners.
  • Ownership gaps: repos with no owner. Fix by making ownership metadata mandatory.
  • Exceptions that never expire: every waiver needs an end date.
  • Developer fatigue: too many noisy checks make people ignore all of them. Tune rules, reduce false positives, and show the fix path inside the PR.
  • Security champions: one volunteer developer per team who acts as the local security friend. This is how a handful of AppSec people reach thousands of developers.

Part 15. Kubernetes in Real Life

15.1 The mental model: an apartment complex

Kubernetes word Apartment-complex analogy Plain meaning
Cluster The whole housing complex A group of machines managed together
Node One building (a real or virtual machine) Where containers physically run
Pod One flat Smallest unit; holds one or more containers
Container The family living in the flat Your app plus what it needs
Deployment The lease rule: always keep 3 flats of this type occupied Says how many copies to run and which image
Service The reception desk with a fixed phone number Stable address, even as flats change
Ingress The main gate Lets outside traffic into the right service
Namespace A wing or block of the complex Logical separation inside a cluster
ConfigMap / Secret Notice board / locked drawer Settings / sensitive values
RBAC Who holds which keys Permissions for people and programs
NetworkPolicy Internal doors between flats Which pods may talk to which
Resource limits Electricity and water rationing Stops one pod starving others

The manager of the complex is the control plane. You tell it the desired state (I want 3 copies of order-service version 5), and it keeps working to make reality match. If a pod dies, it starts another. That constant self-repair is Kubernetes' superpower.

15.2 How clusters are laid out in a big company

Pattern Typical use Notes
One cluster per environment (dev, qa, prod) Common starting point Prod is isolated from experiments
Several prod clusters per region Large traffic, resilience One for India, one for Europe, and so on
Shared cluster, one namespace per team Saves cost Needs strong RBAC, quotas and network policies
Separate cluster for sensitive workloads Payments, regulated data Extra isolation
Regional clusters on GKE, EKS and ACK Multi-cloud companies Same policies, different providers

Multi-tenancy (many teams in one cluster) is like many families sharing a complex. It works only with rules: a team gets its own wing, a quota, and cannot enter another wing.

15.3 Security controls inside Kubernetes

  1. RBAC: no human gets cluster-admin day to day. Developers get read access to their own namespace in prod; changes arrive through the pipeline.
  2. Pod security standards: the restricted profile means non-root, no privileged mode, no extra Linux capabilities, read-only filesystem where possible.
  3. Network policies: start with deny all, then allow only the needed paths (order-service may call payment-service, nothing else).
  4. Secrets: a Kubernetes Secret is only base64-encoded, which is not encryption. Real setups pull secrets from Secret Manager or Vault through an operator or CSI driver, and enable envelope encryption of etcd with a KMS key.
  5. Admission control: Kyverno or OPA Gatekeeper (plus Binary Authorization on GKE) rejects bad pods before they start: unsigned images, images from unknown registries, privileged containers, missing resource limits.
  6. Private clusters: the control plane and nodes have no public exposure; admins reach them through approved paths.
  7. Workload identity: pods talk to cloud services using GKE Workload Identity (or IRSA on EKS, RRSA on ACK) instead of key files.
  8. Audit logs: every API action is recorded and shipped to the SIEM.

What a hardened deployment looks like:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
  namespace: orders-prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: order-service
  template:
    metadata:
      labels:
        app: order-service
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: app
          image: registry.acme.com/orders/order-service@sha256:<digest>
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ['ALL']
          resources:
            requests: { cpu: 250m, memory: 256Mi }
            limits: { cpu: 500m, memory: 512Mi }
          readinessProbe:
            httpGet: { path: /healthz, port: 8080 }

Spot the details: the image is referenced by digest (an unchangeable fingerprint, not a movable tag), it does not run as root, it cannot gain extra powers, and it has resource limits and a health check.

15.4 GitOps: the building plan on the office wall

In GitOps tools (Argo CD, Flux), the desired state of the cluster lives in a Git repo. A supervisor program inside the cluster compares reality with the plan every few minutes and corrects differences.

  • To change production, you open a PR to the config repo. Review and checks happen like any code change.
  • Nobody types kubectl commands into prod. If someone does, the supervisor reverts it (drift correction) and the audit trail shows it.
  • Rollback = revert the commit.

Security win: Git becomes the audit log of everything that ever ran in production.

15.5 Day-two reality

  • Upgrades: Kubernetes versions go out of support; clusters must be upgraded regularly (GKE release channels automate much of it).
  • Node patching: base images and OS patches are refreshed; nodes are replaced, not repaired.
  • Rolling updates: new pods start and pass health checks before old ones stop, so users see no downtime.
  • Autoscaling: more pods at peak time, fewer at night. Black Friday is when this earns its keep.
  • Cost and quotas: security tools must not blow up the cloud bill; agentless scanning is popular partly for this reason.

15.6 Misconfigurations scanners love to find

Privileged containers; containers running as root; hostPath mounts; missing resource limits; default service account in use; cluster-admin bound to normal users; secrets in environment variables of a public manifest; images using the latest tag; a public Kubernetes dashboard or API; no network policies; very old cluster versions.

Part 16. Pipeline Engineering in Depth

16.1 Build once, promote many

A golden rule you met earlier, now with detail:

  • The pipeline builds the image once and records its digest (like a fingerprint).
  • QA, staging and prod all run that exact digest. What was tested is what ships.
  • Environment differences (database address, feature switches, replica counts) are supplied as configuration (Helm values or Kustomize overlays), never by rebuilding.
  • Secrets are fetched at run time per environment from Secret Manager, so a dev secret cannot open prod.

16.2 The promotion ladder

Step Trigger Checks before moving up Who approves
Merge to main PR approved Secret scan, SAST, SCA, unit tests Reviewers and CODEOWNERS
Dev deploy Automatic on merge Smoke test Nobody; automatic
QA deploy Automatic or on demand Integration tests, DAST, API tests QA lead via test results
Staging Release candidate tag Performance test, final policy check Release manager
Prod Scheduled change window Signature verified, no open critical, change ticket linked Named approver, often two people for critical systems

For regulated systems (payments, banking), the change ticket (ServiceNow or Jira) must be linked to the deployment so an auditor can trace who approved what, when.

16.3 Branching in practice

  • Trunk-based development: small, frequent merges to main, protected by strong automated checks. Favoured by modern teams.
  • Release branches or Gitflow: longer-lived branches for scheduled releases. Common in older or regulated products.

Security does not care which you choose, as long as every route to production passes the gates.

16.4 Supply-chain security: protecting the factory itself

Attackers increasingly target the build pipeline and dependencies rather than your code, because one compromise reaches many victims. Real events that shaped today's practice:

  • SolarWinds (2020): attackers inserted malicious code into the build process, so a signed, legitimate update carried a backdoor to thousands of customers.
  • Log4Shell (December 2021): a critical flaw in a ubiquitous Java logging library. The hard question for every company was: where do we use it?
  • Codecov (2021): a modified uploader script in CI leaked secrets from customers' pipelines.
  • tj-actions/changed-files (March 2025): a widely used GitHub Action was compromised and tried to expose pipeline secrets, which is why pinning actions to a full commit SHA is now standard advice.

Defences, in plain language:

Defence Analogy What it gives you
SBOM (SPDX or CycloneDX format) Ingredient list on a packet Instantly answers where a vulnerable library is used
Image signing (cosign, Sigstore) Tamper-proof seal The cluster can verify the image came from your pipeline
Provenance attestation Receipt of who built it, where, from which commit Proves the build was not tampered with
SLSA framework A maturity ladder for build integrity Gives a shared target for how trustworthy builds are
Pin actions by SHA Ordering a specific batch number, not just the product name Stops silent changes to third-party actions
Private registry or mirror Buying from your own approved warehouse Blocks typosquatted or hijacked packages
Lockfiles and hash checking Fixed shopping list Stops surprise dependency versions
Dependency confusion protection Making sure internal names cannot be claimed publicly Prevents attackers publishing a public package with your internal name

16.5 Secrets and cloud login from a pipeline

The old way: paste a long-lived cloud key into GitHub secrets. If leaked, it works forever. The modern way is OIDC federation: GitHub proves who the job is, and the cloud hands out a token valid for minutes.

jobs:
  deploy-dev:
    runs-on: ubuntu-latest
    environment: dev
    permissions:
      id-token: write
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: projects/123456/locations/global/workloadIdentityPools/github/providers/github-oidc
          service_account: deployer-dev@orders-dev.iam.gserviceaccount.com
      - run: echo 'now deploy using short-lived credentials'

The trust rule on the cloud side says only this repo, only this branch or environment may use this service account. The prod service account is a different one, trusting only the prod environment, which itself requires approval. Same idea exists on AWS (OIDC identity provider plus an IAM role) and on Alibaba Cloud (OIDC role for RAM).

16.6 Releasing safely: rolling, blue-green, canary

  • Rolling update: replace pods gradually.
  • Blue-green: two full copies; flip traffic from the old (blue) to the new (green) in one move. Instant rollback by flipping back.
  • Canary: send 1 percent of users to the new version, watch error rates and security signals, then 10, 50, 100 percent.

Fast rollback is itself a security feature, because when a bad release or a new vulnerability appears, the shorter the exposure, the smaller the damage. Feature flags let a risky feature be switched off without redeploying.

16.7 Pipeline hardening checklist

  • Workflow permissions default to read-only; grant more per job.
  • Third-party actions pinned to commit SHA and updated through reviewed PRs.
  • Production environment requires reviewers; self-approval disabled.
  • No secrets exposed to workflows triggered from forks.
  • Ephemeral runners; no shared long-lived credentials on them.
  • Logs never print secrets; masking turned on.
  • Pipeline definition files protected by CODEOWNERS, because whoever edits the pipeline controls what ships.
  • Branch protection prevents bypassing the pipeline.

Part 17. Scanners in Depth and WIZ Day to Day

17.1 How each scanner thinks

  • SAST (CodeQL, Semgrep, SonarQube): turns your source into a model, then asks questions like: does data from an HTTP request (a source) ever reach a database query (a sink) without cleaning (sanitiser)? If yes, that is potential SQL injection. Analogy: an editor tracing a rumour from where it started to where it was printed.
  • SCA (Dependabot, Snyk, Trivy): reads your dependency list, then matches names and versions against vulnerability databases (CVE records, the GitHub Advisory Database). Analogy: comparing grocery labels against a recall list. Better tools also check reachability: does your code actually call the vulnerable function?
  • DAST (OWASP ZAP, Burp): attacks the running QA app from outside with crafted requests, like a mystery shopper trying every door.
  • Secret scanners: pattern matching for known token formats, entropy checks for random-looking strings, and often validation by safely testing whether a key is still live.
  • IaC scanners (Checkov, tfsec, WIZ Code): parse Terraform, CloudFormation and Kubernetes YAML and compare against policies such as no public buckets and no open SSH.
  • Container scanners (Trivy, Grype, WIZ): unpack each image layer, list operating-system packages and libraries, then match against vulnerability data.
  • Cloud posture and workload scanners (WIZ): read cloud configuration through provider APIs and inspect copies of workload disks (snapshots) without installing agents.

17.2 Strengths and weaknesses

Category Finds Typical weakness
SAST Flaws in your own logic False positives; misses runtime and config issues
SCA Known-vulnerable libraries Noisy; many findings are not reachable
DAST Real exploitable behaviour in a running app Needs a working environment; slow
Secrets Leaked credentials Misses custom formats; some false alarms
IaC Misconfiguration before creation Cannot see what was changed by hand later
Container Old packages in images Many OS-level findings with no fix available
Cloud posture (WIZ) What is actually deployed and exposed Cannot tell you the exact line of code, unless linked back to the repo

No single scanner is enough. They are different kinds of inspector.

17.3 Severity is not the same as risk

A vulnerability has a CVSS score (0 to 10) describing how bad it could be in general. Real priority needs more questions:

  • Is it actively exploited in the wild? (CISA's Known Exploited Vulnerabilities list, EPSS probability scores)
  • Is the asset internet-facing?
  • Is it in production and does it hold sensitive data?
  • Is the vulnerable code reachable?
  • Is there a compensating control (WAF rule, network block)?

Example: A CVSS 9.8 flaw in a library inside an internal batch job with no network access and no sensitive data may be less urgent than a CVSS 7.5 flaw on an internet-facing payment API with a powerful role. Context decides.

17.4 Handling false positives without losing trust

  1. Developer marks a finding as false positive with a reason.
  2. AppSec samples and reviews those dismissals, especially for critical code.
  3. Repeated false positives from one rule lead to tuning the rule, not ignoring the tool.
  4. Waivers have an owner, a reason and an expiry date.

Developers keep trusting the pipeline only if it is mostly right and explains itself.

17.5 WIZ in depth

Product names and feature bundles change over time; confirm current capabilities in WIZ documentation before quoting them to a client or manager.

  • Connectors: WIZ connects to cloud accounts through read-only roles (AWS, GCP and others, with Alibaba Cloud among supported clouds at the time of writing). It also connects to Kubernetes clusters and code platforms such as GitHub.
  • The Security Graph: WIZ stores everything as a connected map: a VM is linked to its network exposure, its identity, its vulnerabilities, and the data it can reach. Questions such as show me internet-exposed workloads with critical vulnerabilities and access to sensitive data become simple searches.
  • Findings versus Issues: a finding is a single raw observation (one vulnerability, one misconfiguration). An Issue is a risk worth acting on, built by combining findings along an attack path. Teams work Issues, not raw findings.
  • Controls and policies: Controls are rules (for example, bucket is public). Policies group them for compliance frameworks such as CIS benchmarks, PCI DSS or ISO 27001, and for your own standards.
  • Projects: a way to group cloud resources by team, application or environment. Projects are the bridge to ownership: the Orders team sees only Orders issues, and managers see the status for their area.
  • Automation and ticketing: rules route Issues to Jira, ServiceNow or Slack with the right team, severity and deadline, so security does not manually forward thousands of items.
  • WIZ Code and the pipeline: a CLI and integrations scan IaC, containers, secrets and code in pull requests and CI, set policies that warn or block, and map a cloud resource back to the repo and pipeline that produced it. This is what turns a production finding into a fix in the right repo.
  • Runtime layer: where enabled, a sensor adds live threat detection on workloads, complementing the agentless view.

17.6 A WIZ triage walkthrough

Issue appears: Publicly exposed VM with a critical vulnerability and a highly privileged service account.

  1. Validate: open the graph path. Is the VM really reachable from the internet? Is the vulnerable service running?
  2. Find the owner: use the Project, tags and code-to-cloud mapping to identify the team and the repo.
  3. Contain first if urgent: restrict the firewall rule or remove public access immediately.
  4. Open a ticket to the owning team with the graph link, deadline and fix guidance.
  5. Fix at the source: update the Terraform or image in the repo so the problem does not return.
  6. Verify: confirm the Issue closes after redeployment.
  7. If a fix cannot happen soon: record a time-limited exception with compensating controls and a named approver.
  8. Learn: add a pipeline rule so this class of mistake fails earlier next time.

Part 18. Vulnerability Management: From Finding to Fixed

Finding problems is easy. Getting them fixed across thousands of teams is the real job. Think of a city health department: inspectors find violations, but a process makes sure each shop actually fixes them by a deadline.

18.1 The lifecycle

  1. Detect: scanners, WIZ, bug bounty reports, pen tests, vendor advisories.
  2. Deduplicate and enrich: the same library flaw appears in 300 repos; group it into one problem. Add context: exposure, data sensitivity, exploit activity.
  3. Prioritise: rank by real risk, not by raw score.
  4. Assign: to the owning team through a ticket, with clear fix guidance.
  5. Fix: upgrade the library, patch the image, change the configuration, or add a compensating control.
  6. Verify: rescan; confirm the issue closed in the running environment, not just in the repo.
  7. Report: dashboards for managers, audit evidence for compliance.

18.2 Example remediation deadlines (SLAs)

Every company chooses its own numbers. A typical shape:

Severity (after context) Internet-facing production Internal production Non-production
Critical, actively exploited Hours to 2 days 7 days 30 days
Critical 7 days 14 days 30 days
High 30 days 45 days 60 days
Medium 90 days 120 days Next release
Low Best effort Best effort Best effort

The tighter the exposure, the tighter the deadline. Notice that the SLA depends on where the problem sits, not only on how scary the vulnerability sounds.

18.3 Exceptions done properly

Sometimes a fix is impossible this quarter (a vendor has not released a patch, a legacy system cannot be upgraded). A proper risk exception contains:

  • What the risk is, in plain language.
  • Why it cannot be fixed now.
  • Compensating controls (extra monitoring, network restriction, WAF rule).
  • A named risk owner who accepts it (a business owner, not only an engineer).
  • An expiry date and a review.

Exceptions without expiry dates become permanent holes.

18.4 Patch cadence in the real world

  • Microsoft Patch Tuesday and SAP Patch Day both fall on the second Tuesday of the month, so many security teams plan their monthly cycle around them.
  • Out-of-band emergencies (a Log4Shell-style event) override the calendar; the incident process takes over.
  • Containers are patched by rebuilding the image with updated base layers and redeploying, not by logging in to fix running containers.

Part 19. When Things Go Wrong: An Incident, Minute by Minute

19.1 How incidents are organised

Role Job
Incident commander Runs the response, makes decisions, keeps people focused
Technical lead(s) Investigate and fix
Communications lead Updates management, legal, customers, regulators
Scribe Writes the timeline as it happens
Business or product owner Weighs business impact and trade-offs

Severity levels (example): Sev1 = customer data or major revenue at risk; Sev2 = significant but contained; Sev3 = minor. Higher severity wakes more people and starts legal and compliance clocks. For example, many laws require breach notification within a fixed time window, which is why the timeline matters.

19.2 Scenario: a cloud key leaks into a public repo

A developer in acme-sandbox pastes a working AWS key into a README on a public repo. Here is the response:

Time What happens
02:10 A secret scanner alerts: valid cloud key in a public repo. Automatic ticket to the on-call security engineer.
02:15 On-call confirms the key is live and finds its owner and permissions. It belongs to a service account with write access to an S3 bucket in a non-prod account.
02:20 Contain: key disabled. Repo made private. This happens before anything else, because bots scrape new commits within minutes.
02:30 Cloud audit logs show the key was used from an unknown IP at 02:07 to list buckets, and three downloads occurred.
02:45 Severity raised. Bucket contents are reviewed: test data only, no customer data. Scope stays contained.
03:30 Eradicate: all keys for that service account rotated; role permissions trimmed; other repos searched for the same key.
Next day Recover and notify: developer and manager informed; legal notified for the record; no customer impact.
Within a week Blameless post-mortem: why was a long-lived key possible at all? Actions: enforce push protection, move to OIDC and short-lived roles, add an SCP that blocks long-lived key creation in sandbox accounts.

The lesson: speed of containment mattered more than speed of investigation. And the root fix was removing the possibility, not punishing the person.

19.3 The incident response loop

Prepare, detect, contain, eradicate, recover, learn. Preparation (runbooks, contact lists, practised drills, good logs) decides how calm the other five phases are. A company that has never rehearsed will discover its gaps at 2 AM.

19.4 Logs you wish you had

Cloud audit logs (GCP Audit Logs, CloudTrail, ActionTrail), Kubernetes audit logs, GitHub audit log, identity provider sign-in logs, load balancer and WAF logs, and application logs. All are sent to a central SIEM and kept for a defined period. If logging was never enabled, the investigation is blind. Logging is an advance investment.

Part 20. Case Study: Acme Retail Ships a Black Friday Feature

Acme wants a new Buy Now, Pay Later option live before Black Friday. Follow it across eight weeks and see where DevSecOps shows up.

Week 1: Idea and design

Product, architects and AppSec meet. New feature means new risk: money, personal data, a new third-party lender integration. Threat modelling asks: what could go wrong? Fraudulent applications, tampered amounts, leaked personal data, lender API outage. Security requirements go into the tickets: encryption of personal data, rate limits, strong authorisation, audit logging.

Weeks 2 to 4: Build

A new microservice, bnpl-service, is created from the golden template in acme-retail-apps. The pipeline is inherited from the central reusable workflow, so scanning is on from commit one. Developers use VS Code and PyCharm with security plug-ins. Every PR passes secret scan, CodeQL, dependency review and unit tests. A vulnerable JSON library is caught in week 2 and upgraded in minutes, because it was caught at the PR, not at launch.

Meanwhile the platform team uses Terraform in acme-platform to create the new database and a private service-to-service route. IaC scanning blocks a draft that exposed the database port too widely.

Week 5: Testing in QA

The image, built once, is deployed to the QA cluster. Testers run functional tests. A DAST scan hits the API and finds that one endpoint returns detailed error traces. It is fixed. Performance tests simulate Black Friday traffic. An independent penetration test on the staging environment finds an authorisation gap that lets one user view another user's instalment plan. This is the exact broken-access-control issue from Part 12, now fixed before release.

Week 6: Release readiness

A checklist is reviewed: threat model done, critical findings closed, secrets in Secret Manager, signed image, SBOM stored, runbook written, monitoring dashboards and alerts ready, rollback tested, privacy review complete, change ticket approved. WIZ is checked: no open critical issue on the new project, no public exposure.

Week 7: Production rollout

In the approved change window the release manager approves. The cluster admission controller verifies the image signature. A canary sends 1 percent of traffic, then 10, then 50. Dashboards show error rates and unusual authentication patterns. Feature flag keeps the lender integration switched off until the final hour.

Week 8: Black Friday and after

The SOC watches for fraud and abuse patterns. Autoscaling absorbs the peak. A new library vulnerability is announced on the Tuesday after; the SBOM and WIZ show within an hour that bnpl-service is affected, the owning team gets a ticket, a patched image goes through the same pipeline and reaches prod within the SLA. A short retrospective captures what worked and what to improve.

What this proves: security was never a single gate at the end. It was present in design, code, infrastructure, test, release and operations. That is what DevSecOps means in a real organisation.

Part 21. Governance, People and How Security Really Gets Done

21.1 From policy to pipeline

Rules in a large company come in layers:

Layer Meaning Example
Policy What must be true, and why All production code is scanned before release
Standard The specific requirement Critical SAST findings block merge; secrets must live in the approved vault
Procedure Step-by-step how How to request an exception, how to rotate a key
Guideline Friendly advice How to write secure input validation in Java
Control in the pipeline The automatic enforcement CodeQL job with a failing check

A policy nobody can enforce is a poster. A policy turned into automation is real security. This conversion, policy to pipeline, is much of the DevSecOps engineer's craft.

21.2 Frameworks and audits you will hear about

  • OWASP Top 10, ASVS and SAMM: application-security risks, verification requirements and maturity model.
  • NIST Cybersecurity Framework and NIST SSDF: general security and secure software development guidance.
  • ISO 27001, SOC 2: organisation-wide security management and assurance reports customers ask for.
  • PCI DSS: required if you handle payment card data.
  • CIS Benchmarks: concrete hardening settings for clouds, Kubernetes and operating systems.
  • DPDP Act (India), GDPR (EU): privacy laws about personal data.

Auditors ask for evidence: logs, tickets, screenshots, configuration exports. A pipeline that automatically stores scan results and approvals produces audit evidence as a by-product.

21.3 A day in the life of each role

Developer (Ravi): pulls the latest code in VS Code, builds a feature, sees SonarLint hints, opens a PR, fixes a dependency alert, responds to review comments, watches the QA deployment. Security is a part of the normal flow when it is fast and clear.

DevOps or platform engineer: maintains reusable workflows, upgrades the Kubernetes clusters, rotates runner images, fixes a failing pipeline for three teams, reviews a Terraform change.

AppSec analyst: tunes CodeQL and WIZ Code rules to cut false positives, reviews a risky design, runs a secure-coding session, triages a high-severity finding with a developer, updates the exception register, reports weekly metrics.

Cloud security engineer: reviews WIZ Issues by attack path, hardens organisation policies, investigates an overly broad role, checks new accounts were created with the landing zone guardrails.

SOC analyst: watches alerts, investigates a suspicious sign-in, pivots through audit logs, escalates to incident response.

Release manager: checks the readiness list, confirms the approvals, runs the change window.

21.4 Working with developers: the human side

Tools do not secure a company by themselves. People do. Habits of effective security teams:

  • Make the secure way the easy way: golden templates, one-line pipeline calls, auto-fix PRs.
  • Explain, do not just reject: a failing check should say what is wrong, why it matters, and how to fix it.
  • Respect delivery pressure: offer a safe fast path and a clear exception route, not a wall.
  • Measure and share progress: friendly dashboards by team, with wins celebrated.
  • Train in context: short sessions using the team's own code and real findings.
  • Blameless culture: mistakes are system failures to fix, so people report problems early.

Part 22. Advanced Labs and Learning Roadmap

Lab 2: Two-cluster promotion with GitOps

Create two local clusters (or two namespaces) named qa and prod. Install Argo CD. Put your manifests in a config repo. Make the pipeline update the image digest in the config repo through a PR; let Argo CD apply it. Add a required reviewer for the prod folder. Try changing something in prod by hand and watch the drift correction.

Lab 3: Admission policies

Write Kyverno policies that reject: images not from your registry, containers running as root, pods without resource limits, and images without a valid signature. Deploy deliberately bad manifests and read the rejection messages. Then fix the manifests until they pass.

Lab 4: Supply-chain hardening

Generate an SBOM in the pipeline, sign the image with cosign, attach provenance, and verify the signature at deploy time. Pin all actions by SHA. Switch cloud authentication to OIDC and delete any stored keys.

Lab 5: Incident drill

Plant a fake key in a sandbox repo, let your secret scanner find it, and run the response from Part 19: revoke, check logs, rotate, write a one-page post-mortem. Time yourself.

Lab 6: Prioritise like a pro

Take a list of 20 sample findings (mix of critical and medium, internet-facing and internal, with and without sensitive data). Rank them using the questions in Part 17.3 and justify the top five. Compare with a friend or colleague and discuss differences.

Capstone project

Build a small three-service application (frontend, order API, database) with three environments, a reusable pipeline, scanning at every stage, signed images, GitOps deployment, policy enforcement, a documented exception process, a dashboard of metrics and an incident runbook. Present it as if briefing a new colleague. If you can explain it in plain language, you have understood it.

Suggested study order

  1. Linux, networking basics (IP, DNS, HTTP, TLS), Git.
  2. Docker and containers.
  3. CI/CD with GitHub Actions.
  4. Kubernetes basics, then Kubernetes security.
  5. One cloud deeply (start with GCP or AWS), then translate to the others.
  6. Application security: OWASP Top 10, threat modelling.
  7. Supply-chain security, IaC security, policy as code.
  8. Cloud security posture and attack-path thinking with tools like WIZ.
  9. Incident response and communication skills.

Useful structured credentials when you want proof of learning include Certified Kubernetes Security Specialist (CKS), Google Professional Cloud Security Engineer, and AWS Certified Security Specialty. They help, but a working lab you can demonstrate is worth more than any badge.

Extended Glossary

  • Admission controller: the gatekeeper that checks every new object entering a Kubernetes cluster.
  • Attack path: a chain of weaknesses that together lead an attacker to something valuable.
  • Break-glass account: emergency access, heavily watched, used only when normal paths fail.
  • Canary release: sending a small share of traffic to the new version first.
  • CIEM: cloud infrastructure entitlement management, the study of who can do what in the cloud.
  • CSPM: cloud security posture management, spotting risky cloud settings.
  • CVE / CVSS / EPSS / KEV: the ID of a known flaw / its general severity score / probability it will be exploited / list of flaws known to be exploited.
  • Digest: an unchangeable fingerprint of a container image.
  • Drift: when real infrastructure differs from what the code says it should be.
  • Egress: traffic leaving a network.
  • GitOps: operating infrastructure by changing Git and letting automation apply it.
  • IDOR: insecure direct object reference, such as changing an order number in a URL to see someone else's order.
  • Landing zone: the pre-configured, guarded starting point for new cloud accounts.
  • mTLS: both sides of a connection prove their identity and encrypt traffic.
  • Provenance: a record of how and where software was built.
  • SCP / Organization Policy: rules set above accounts or projects that limit what anyone inside can do.
  • SIEM: the central system that collects and analyses security logs.
  • SLSA: a framework of levels for build and supply-chain integrity.
  • Toil: repetitive manual work that automation should replace.
  • Typosquatting: publishing a malicious package with a name almost identical to a popular one.
